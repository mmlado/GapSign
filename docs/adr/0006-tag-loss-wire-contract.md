# 0006. Tag-loss wire contract: promise rejection carrying upstream's message literals

Date: 2026-08-12
Status: accepted

## Context

When the Keycard leaves the NFC field mid-APDU, the native bridge
(`react-native-keycard`) must tell the JS layer that this was a recoverable
tag loss, not a card error. Three contract shapes were considered:

1. A third `state` value in the resolved response (`{ state: 'disconnected' }`).
2. A promise rejection with a dedicated reject code (`E_KEYCARD_TAG_LOST`).
3. A promise rejection whose **message** contains upstream's own literals:
   `"Tag was lost."` on Android (the Android framework's `TagLostException`
   message) and `"NFCError:<code>"` on iOS (the format
   `react-native-status-keycard` has shipped for years).

The failure mode that decides this: the bridge's `lib/` build output is
gitignored and generated by `prepare: bob build` at install time, so the
installed JS can be **stale** relative to the native sources (this happened in
this repo during design, verified against the lock file).

## Decision

Shape 3. The bridge rejects; the classification signal is the rejection's
message, matched in Pal by `isTagLostError` (`src/utils/keycardErrors.ts`).
The literals belong to upstream and must never be paraphrased on either side.

## Rationale

- A resolved third `state` breaks catastrophically under a stale `lib/`:
  the old `CardChannel.js` only tests `state === 'error'`, and constructs
  `APDUResponse` outside its try, turning tag loss into an unrelated crash.
- A reject code is dead on arrival: keycard-sdk's `CardIOError` stringifies as
  `'CardIO Error: ' + err`, which preserves the message but **discards
  `err.code`**. Only the message survives every wrapper on the path
  native reject -> TurboModule Error -> CardChannel wrap -> keycard-sdk rethrow
  (each hop verified against RN 0.83 and keycard-sdk 3.1.9 sources).
- Matching upstream's own strings means the contract also matches what
  status-legacy's field-proven `tag-lost?` predicate has always matched.

## Consequences

- `isTagLostError`'s message list is **closed**: a false positive traps the
  user in a reconnect wait. New strings require evidence from the emitter.
- Renaming those literals upstream would silently disable classification in
  Pal; the bridge contract test (planned with the bridge PR) exists to make
  that a red build instead.
- The predicate keeps inert `code`/`name` arms as forward compatibility only;
  nothing may assume they fire.

## Revisit

If the bridge ever ships typed error classes end to end (and the stale-`lib/`
hazard is closed by a contract test), a typed contract may replace message
matching.
